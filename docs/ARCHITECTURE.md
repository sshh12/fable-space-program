# Architecture

Definitive architecture for the true-scale Earth/Moon spaceflight simulator. `PROMPT.txt` is the binding
requirement; the documents in `docs/research/` are the detailed designs this file builds on. **Where a
research document disagrees with this file, this file wins.** Where this file is silent, the research
document for that area applies (`sim-design.md`, `rendering-design.md`, `earth-data.md`,
`moon-sky-data.md`, `webgpu-harness.md`).

The shared contracts described here exist as compiling TypeScript in `src/core/contracts/` and are the
source of truth for every interface named below.

architect/integrator. **Nobody edits outside their own paths.** A needed change to someone else's path

Import rules (enforced in review):

- `src/core` imports nothing outside `src/core`.
- `src/sim`, `src/terrain`, `src/pilot` are headless: no DOM, no WebGPU, no `performance.now`, no
  `Date.now`, no `Math.random`. They import only `src/core` (and each other where stated: `sim -> terrain`
  only through the `TerrainProvider` contract; `pilot -> sim` only through the `Sim` contract).
- Render packages import `src/core` and the public API of `src/render/core`; never each other. They
  exchange GPU data only through `SharedResources`.
- `src/ui`, `src/map`, `src/audio`, `src/input`, `src/camera` import `src/core` only (plus
  `src/render/core` public helpers where a GPU pipeline is needed).
- Only `src/app` knows every subsystem.
- Path alias: `@/` = `src/`.

Repo etiquette for parallel work in one working tree:

- Verify with scoped commands so other teams' work in progress cannot break you:
  `npm run typecheck:paths -- <your paths>`, `npx vitest run <your paths>`,
  `npx playwright test tests/browser/<package>`. Do not run `npm run build` (it writes the shared `dist/`).
- Browser tests start their own dev server on a free port (`tests/browser/globalSetup.ts`); never start a
  long-lived server and never hard-code a port.
- Commit only your own paths (`git add <paths>`; never `git add -A`, `git stash`, `git reset`,
  `git checkout .` or history rewrites). Retry on `index.lock`. Never commit `.env`, `data/tiles`,
  `data/sky`, `data/cache`.
- Secrets are read from `.env` by build-time tools only (Node/Python under `tools/`); nothing under `src/`
  or `public/` may contain or fetch a key.
- No placeholders, stubs or TODO comments in delivered code. If something cannot be finished, say so in
  the hand-off report instead of leaving a stub.

## 3. Conventions

**Units.** SI everywhere in code: metres, seconds, kilograms, newtons, kelvin, pascals, radians. Data files
use degrees for angles (field names end in `Deg`) and are converted at load. Rendering is photometric:
luminance in cd/m^2, illuminance in lux.

**Time.** `ut` = seconds since J2000.0 (2000-01-01T12:00:00, treated as UTC), float64. Simulation time
advances only through the sim; wall-clock time is used only for presentation (animation of noise, UI).
The physics step is fixed at `PHYSICS_DT = 1/120 s`; warp levels are `WARP_LEVELS` (indices 0-3 physics
warp, 4-10 rails warp).

**Handedness and frames.** Everything is right-handed.

| Frame | Origin | Axes |
|---|---|---|
| ROOT | centre of the root body (Earth) | inertial; +Z = Earth north pole, +X = J2000 vernal equinox |
| BCI(b) | centre of body b | parallel to ROOT (never rotates) |
| BCBF(b) | centre of body b | body-fixed; +Z spin axis, +X prime meridian on the equator |
| ENU(p) | a surface point | +X east, +Y north, +Z up (geocentric vertical) |
| VES | vessel root part origin | +Y nose (thrust direction), +X starboard, +Z dorsal |
| part | part origin | same axis meaning as VES; placed by `PartSnapshot.localPos/localRot` |
| view | camera eye | +X right, +Y up, camera looks down -Z |
| render world | camera eye | axes parallel to ROOT ("camera-relative") |

Latitude is planetocentric, longitude east-positive; `dir = (cos lat cos lon, cos lat sin lon, sin lat)` in
BCBF. Bodies are spheres of `BodyDef.radius` for the physics datum; terrain height is added radially.

Body orientation follows the IAU form `R(BCBF->BCI) = Rz(alpha0 + 90deg) Rx(90deg - delta0) Rz(W)` with
pole right ascension/declination `alpha0, delta0` and prime-meridian angle `W = w0 + rate (ut - epoch)`.
Tidally locked bodies solve `W` from their orbit (`sim-design.md` 2.2).

**Quaternions** (`src/core/math/quat.ts`): Hamilton, stored `{x, y, z, w}`. `rotate(q, v)` is the active
rotation. A quaternion named `qAToB` maps components in frame A to components in frame B. `mul(a, b)`
applies `b` first, so `qAToC = mul(qBToC, qAToB)`. The vessel attitude `q` is VES -> ROOT.

**Matrices.** `Mat3` is row-major float64 (CPU maths, inertia). `Mat4` is column-major (WGSL layout).
The one projection is `mat4.perspectiveReversedZInfinite(fovY, aspect, 0.05)`.

**Control signs** (VES): pitch + = nose toward +Z (up); yaw + = nose toward +X (right); roll + = rotation
about +Y (clockwise seen from behind). On the pad the ventral side (-Z) faces `padAzimuthDeg`, so pitching
down tips the nose down-range.

**Ids** are lower-kebab strings. Engine code never mentions a specific body, vehicle, part or site id.

**Determinism.** `src/sim`, `src/terrain` and `src/pilot` iterate in array order and use only the seeded
integer hash / PRNG in `src/core/math/hash.ts`. Same scenario + same call sequence = bit-identical state.

## 4. Precision

- All positions are float64 on the CPU. Vessel state is relative to its SOI body (|r| < 4.5e8 m gives
  6e-8 m resolution), so the physics needs no origin shifting.
- The GPU never sees a planet-scale coordinate of anything drawn at high detail. Each frame the CPU
  computes `objectOrigin - cameraEye` in float64 (`FrameContext.bodyPose/vesselPose`) and narrows to
  float32; shaders add small local offsets. The view matrix is rotation-only.
- Terrain vertices use the cancellation-free tile formula and atmosphere shaders the stable altitude
  formula of `rendering-design.md` 2.3. Planet-fixed tiling coordinates are sent modulo a period computed
  in float64.
- Depth: a single reversed-Z, infinite-far `depth32float` pass with near = 0.05 m
  (`RENDER_FORMATS.depth`, `NEAR_PLANE`); compare `greater`, clear 0, sky test `depth == 0`. No depth
  partitioning and no scene swaps: cockpit, terrain, Moon and stars are one scene.
- Motion vectors are built from the previous frame's float64 camera and body states
  (`FrameContext.prevViewProj`, `prevEyeOffset`, `BodyPose.prev*`).
- Hash-critical maths that must agree between TS and WGSL uses 32-bit integer arithmetic only
  (`hashU32`, `HASH_WGSL`). Vectors from near-parallel large operands are normalised before crossing.

## 5. Runtime data flow

One frame of the app loop (`src/app`, wired by the lead through contracts only):

```
requestAnimationFrame(now)
  realDt = clamp(now - last, 0, 0.1 s)
  input        = inputSystem.sample()                       InputFrame (device-independent actions)
  controls     = controller.update(input, lastSnapshot, sim.commands, realDt)     ActiveController
  sim.setControls(controls)
  sim.advance(realDt, onControlTick)                        0..N fixed steps or one rails advance;
                                                            onControlTick runs the scripted pilot when enabled
  snapshot     = sim.snapshot()                             immutable; drains events exactly once per frame
  camera       = rigs[viewMode].update(snapshot, cameraInput, realDt)             CameraState (f64)
  mapView.update(snapshot, camera, sim.commands, pointer)   only in map view; edits nodes via PlayerCommands
  hud.update(snapshot, viewMode, realDt)
  audio.update({ snapshot, listener(camera), realDt, warpFactor })
  renderer.render(snapshot, camera, observers, realDt)      frame graph (section 10)
  testApi.frameDone()
```

- **The snapshot is the only thing that flows from the simulation to presentation.** Consumers never hold
  references into sim internals and never mutate a snapshot.
- **`ControlInputs` + `PlayerCommands` are the only things that flow back.**
- The renderer keeps the previous snapshot and camera for motion vectors and interpolation-free rendering
  (the sim advances by whole steps; at 60 fps and 120 Hz physics that is exactly 2 steps per frame).
- Events (`SimSnapshot.events`) are edge-triggered facts (ignition, staging, touchdown, part destroyed);
  continuous state (throttle, heat, chute inflation) is read from the snapshot every frame.
- Time warp never changes this flow: physics warp runs more steps per frame; rails warp replaces stepping
  by an exact Kepler advance clamped to the next event.

## 6. Simulation

Design: `docs/research/sim-design.md` (authoritative for formulas, numbers and the vehicle). Structure:

- **sim-orbits** (`src/sim/orbit, frames, bodies, nav`): universal-variable Kepler propagation, elements,
  event finding (SOI entry/exit, atmosphere entry, terrain impact, radius crossings), patch prediction
  across SOI changes with maneuver nodes, closest approach, body ephemerides and rotation, USSA-76 /
  table / exponential atmospheres, navball and readout maths, launch-window maths. Pure functions of state.
- **sim-vessel** (`src/sim/vessel, dynamics, control`): part tree and assembly, mass properties, resources,
  engines/gimbal/RCS/reaction wheels, staging actions and vessel splitting, aerodynamics, aerothermal
  heating and ablation, g-loads and structural failure, parachutes, landing legs, penalty contact,
  buoyancy, SAS and actuator allocation, the fixed-step integrator. It sees the world only through
  `VesselEnvironment` (`src/core/contracts/simInternal.ts`).
- **sim-world** (`src/sim/world`): the `Sim` implementation. Owns the vessel list and active vessel,
  rails/integrated/landed switching, warp rules and event look-ahead, SOI transitions, debris fidelity
  tiers, milestone detection, patch refresh policy, snapshot building, `PlayerCommands`, the cheat counter
  and the state hash. Factory: `createSim(defs, scenarioId, { terrain })` exported from `src/sim/index.ts`.

Key rules: point-mass gravity of the current SOI body both on rails and when integrating (mode switches
are exact); rails propagation always from the epoch state (no drift at 100,000x); physics warp = more
steps, never a bigger step; contact sub-steps at 480 Hz; terrain collision through `TerrainProvider`
only; the atmosphere co-rotates with the body; Earth rotation gives the pad its 439 m/s.

`SimSnapshot.scenario.startKind` records how the run began. Only a `pad` start with
`stagesAlreadyFired = 0` and `cheatCounter = 0` counts as a mission proof; other scenario kinds exist for
labs, training and visual QA.

## 7. Terrain and tile data

### 7.1 Tile sets

A tile set lives under `data/tiles/{tileset}/` and is served at `/tiles/{tileset}/`:

```
manifest.json                                   TileManifest (src/core/contracts/terrain.ts)
{layer}/{face}/{level}/{x}/{y}.{ext}            tiles; face 0..5 = +X,-X,+Y,-Y,+Z,-Z; x,y in [0, 2^level)
globals/...                                     whole-body equirect maps listed in manifest.globals
```

Mapping: `dir = normalize(N + s U + t V)`; tile-local `(u, v)` to `(s, t)` as in `cubeSphere.ts`. For every
raster layer the column index increases with `u` and the **row index increases with `v`** (row 0 is the
low-`t` edge), so texture coordinates equal tile `(u, v)` for every layer. Equatorial-face tiles therefore
look south-up in an image viewer; that is intended.

| Layer | Encoding | Registration | Content |
|---|---|---|---|
| `height` | `frt1-height` (`.hgt`) | 259 x 259: 257 vertex samples + 1 border sample each side; sample (i, j) at u = (i-1)/256, v = (j-1)/256 | metres above the reference radius; bathymetry is the solid surface |
| `albedo` | `webp` | 256 x 256 texel centres | sRGB base colour without baked shading; alpha = water mask (255 water) when `alpha: 'waterMask'` |
| `night` | `webp` | 256 x 256 | emitted night-light colour (sRGB) |
| `landcover` | `frt1-u8` (`.u8`) | 256 x 256 | `LANDCOVER_CLASS` ids |

Coverage: levels `0..globalMaxLevel` exist everywhere; deeper tiles exist where `coverage[level]` rectangles
say so, and the pyramid is complete (every tile's parent exists). `layerHasTile()` is the single test; the
client never requests a tile the manifest does not promise, and a 404 for a promised tile is a bake bug.

Planned content (final numbers are recorded in each manifest):

| Tile set | Layer | Global levels | Regional levels | Sources |
|---|---|---|---|---|
| earth | height | 0-7 (305 m/sample), scale 0.5 m | 8-12 within 100 km of the launch site (9.5 m/sample), scale 1/8 to 1/16 m | GEBCO 2025 or ETOPO 2022; Terrarium/3DEP |
| earth | albedo | 0-7 (305 m/px) | 8-12 near the site (9.5 m/px) | Blue Marble NG; Sentinel-2 cloudless (CC BY-NC-SA, swappable) |
| earth | night | 0-5 | - | Black Marble |
| earth | landcover | 0-5 (heuristic classes) | 8-12 near the site | ESA WorldCover |
| earth | globals | `cloudCoverage` 8192 x 4096 (coverage, cloud-top/type), `albedoLowRes` 1024 x 512 | | geostationary/cloud composites |
| moon | height | 0-6 (166 m/sample), scale 0.5 m | 7-9 (SLDEM2015) and 10-12 (NAC DTM, 2.6 m/sample) around the landing region | LOLA 118 m; SLDEM2015; LROC NAC DTM |
| moon | albedo | 0-7 (83 m/px; SVS colour x de-shaded WAC detail) | - | SVS CGI Moon Kit; LROC WAC |
| moon | globals | `albedoLowRes` 1024 x 512 | | |

Total baked data stays under 20 GB including caches; raw downloads are deleted after a bake.

### 7.2 The height authority

One implementation in `src/terrain` (`TerrainProvider`) answers every height question:

```
heightAt(body, dir, lambdaMin?) = bicubic(deepest resident data tile)
                                + terrain modifiers (site pad flattening, BodyDef.terrain.modifiers)
                                + band-limited procedural amplification with wavelengths >= lambdaMin
                                  (BodyDef.terrain.amplification: model + seed + params)
```

- Terrain workers call it per tile with the tile's band limit (2 quads) to bake geometry heights and normal
  maps. Rock and crater placement use the same hash. The renderer has no private copy of any of it.
- **Collision surface = rendered surface.** `heightAt` without a band limit returns the bilinear
  interpolation of the height function on the vertex grid of the body's max-render-level tiles - exactly
  the mesh drawn at full detail (difference < 3 cm). Those grids are cached around vessels, so contact
  probes are cheap. Altimetry and prediction far from the ground pass a band limit and get the analytic
  function without fine detail.
- Amplification starts below the data resolution the manifest offers at a point (not below whatever level
  happens to be resident), so detail never doubles up while finer data is streaming.
- Queries are synchronous and never wait for I/O; `ensureLoaded()` preloads around vessels and
  `residency()` reports whether final data is in. The sim clamps warp to 1x if a vessel is below 300 m
  radar altitude without final data (asserted never to happen in scripted missions).
- A coarse level (`manifest.residentHeightLevel`) is always resident for impact prediction.
- Tile bytes come from a `TileSource`: fetch-based in the browser and workers, fs-based in vitest and tools.
- Launch-site pads become `flattenDisc` modifiers automatically (from `LaunchSiteDef.pad`), so the pad is
  flat for both physics and rendering.

### 7.3 Streaming

`src/render/terrain` owns the quadtree, LOD selection per observer, the worker pool, GPU tile pools,
priorities, prefetch and eviction (`rendering-design.md` section 4). New tiles enter fully morphed and
relax, parents are pinned, levels 0-3 are loaded at boot: there is always something correct to draw and
never a pop or a loading screen.

## 8. Sky data

`data/sky/manifest.json` (`SkyManifest`): a Milky Way cube map (raw `rgb9e5ufloat` faces with mips, WebGPU
cube order, ROOT = J2000 equatorial axes) and a binary star catalogue (`STAR_RECORD_FLOATS` float32 per
star: direction, illuminance in lux, colour, magnitude). Stars brighter than the catalogue cutoff are
removed from the cube map. The Sun is defined by `BodyDef.emission`; no texture.

## 9. Data-driven definitions

Everything about the world is data under `data/defs/` (types in `src/core/contracts/defs.ts`, loader in
`src/core/defs/loader.ts`):

```
bodies/{id}.json        BodyDef: mass, radius, orbit, rotation, atmosphere, ocean, terrain, warp limits, render
sites/{id}.json         LaunchSiteDef: body, location, pad, structures, recovery zones
parts/{id}.json         PartDef: mass, shape, attach nodes, resources, aero, thermal, contact, buoyancy, modules, visual
vehicles/{id}.json      VehicleDef: part tree, flow groups, stage stack, abort sequence, crew, cameras, cockpit
scenarios/{id}.json     ScenarioDef: vehicle + site + start time/kind + target
resources.json          ResourceDef[]
render/, terrain/, visuals/, audio/      section files pulled in by "$ref" (owned by the team that tunes them)
regions/{id}.json       bake region manifests (which high-resolution areas to bake, from which sources)
```

- File name = id. Files with an extra dot segment (`earth.atmosphere.json`) are sections, not definitions.
- `{ "$ref": "relative/path.json", "optional"?: true }` is replaced by the referenced file at load. This is
  how one definition is assembled from sections with different owners.
- The dev server lists the directory at `/defs/index.json`; nothing is registered by hand.
- `validateLibrary()` checks cross references; each subsystem validates the sections it consumes and
  reports errors with the file path.

File owners: `bodies/*.json`, `sites/ka-lae-lc1.json` lead; `sites/*.location.json`, `regions/earth-*.json`
bake-earth; `regions/moon-*.json` bake-moon-sky; `terrain/*.amplification.json` terrain-core;
`render/*.surface.json` terrain-render; `render/*.atmosphere.json`, `render/*.clouds.json`
atmosphere-clouds; `render/*.ocean.json` ocean; `resources.json`, `parts/`, `vehicles/` sim-vessel;
`scenarios/` sim-world-pilot (start time from the sim-orbits search tool); `visuals/parts/`,
`sites/*.structures.json` vehicle-pad; `visuals/plumes.json` vfx; `visuals/cockpits/` cockpit; `audio/` audio.

The library must stay loadable at every commit (the app shell and many tests load it): add resources
before parts, parts before vehicles, vehicles before scenarios.

Adding content later:

- **A new moon or planet**: a `bodies/x.json` (+ render/terrain sections), a baked tile set, nothing else.
  Atmosphere, ocean, clouds, night lights are per-body options; the renderer and sim iterate bodies.
- **A new vehicle**: part files + a vehicle file (+ visuals). New part behaviour = a new `ModuleDef` member
  with its implementation in `src/sim/vessel/modules`.
- **A new launch site**: a site file, a region bake, structures from the generator library.
- **A new mission**: a scenario file. Milestone ids are plain strings.

## 10. Rendering

Design: `docs/research/rendering-design.md`. Raw WebGPU + WGSL, no engine. Contracts:
`src/core/contracts/render.ts`. The render core writes `docs/RENDER_API.md` (exact WGSL struct layouts,
bind group 0, helper APIs) for feature authors.

Frame graph (owned by `src/render/core`; features plug in through `RenderFeature` hooks):

| Order | Stage | Hook | Notes |
|---|---|---|---|
| 0 | CPU prepare | `prepare` | culling, streaming, uniform uploads, light registration |
| 1 | Compute | `compute` | atmosphere LUTs, ocean FFT, particle sim, env probe |
| 2 | Sun shadow cascades | `drawShadow` | 8 log cascades, staggered updates |
| 3 | G-buffer | `drawGBuffer` | terrain, far water, vehicles, pad, rocks, cockpit; emissive straight to HDR |
| 4 | AO + contact shadows, deferred lighting | core | sun (with atmosphere transmittance, eclipses, cloud shadow), sky irradiance, IBL, planetshine, local lights |
| 5 | Water forward | `drawWater` | near-field ocean with refraction |
| 6 | Background | `drawBackground` | stars, Milky Way, sun disc, distant bodies where depth == 0 |
| 7 | Atmosphere + clouds | `compositeAtmosphere` | unified per-pixel march from ground to space |
| 8 | Transparents | `drawTransparent` | plumes, plasma, smoke, particles, canopies, glass |
| 9 | TAA/TAAU, bloom, exposure, AgX tonemap | core | dynamic resolution on GPU time |
| 10 | LDR overlay | `drawOverlay` | orbit lines, markers; crisp, after tonemap |

- Targets and encodings are fixed by `RENDER_FORMATS`; material ids by `MATERIAL_ID`.
- Features publish/consume GPU resources through `SharedResources` (transmittance LUT, sky irradiance,
  cloud shadow, env probe, ocean cascades, navball texture, MFD textures, shadow cascades, scene depth).
  The core provides neutral defaults so each feature runs alone in its lab.
- There is exactly one scene. Cockpit, chase and map are cameras into it. The map view shows the real
  bodies at whatever LOD the distance selects.
- Bodies/vessels are iterated generically; shaders take per-body parameters from uniforms built from
  `BodyDef.render`.
- Every pass has a GPU timestamp query; `window.__perf` exposes `PerfSnapshot`.

## 11. Controls and input

```
DOM events -> src/input (binding table, event.code) -> InputFrame (AxisAction / ButtonAction)
           -> ActiveController (FlightController) -> ControlInputs + PlayerCommands -> Sim
scripted pilot (src/pilot)  ------------------------^   same two interfaces, nothing else
Playwright: real key presses through the binding table, or window.__test.setControls / .commands
```

- `ControlInputs`: pitch, yaw, roll, RCS translation, throttle lever. `PlayerCommands`: stage, abort, SAS
  on/off and mode, RCS, legs, lights, fine control, navball mode, warp level, maneuver-node add/edit/remove,
  target, vessel cycling. Every command is reachable from a key or on-screen control.
- Key bindings are a data table (`sim-design.md` section 20): W/S A/D Q/E, Shift/Ctrl/Z/X, Space,
  Backspace, T, R, G, U, Alt+1..8 SAS modes, I/K J/L H/N, CapsLock, `.` `,` `/`, M, C, Tab, `[` `]`.
- The pilot implements `Pilot`; it reads only the snapshot (what the HUD and map show) and plans maneuvers
  by editing nodes and reading the predicted patches, as a player does.
- There is no API that writes vehicle state. `Sim.debug` exists for labs, increments `cheatCounter`, and is
  never reachable from `window.__test`.

## 12. Views and cameras

`ViewMode = 'cockpit' | 'chase' | 'map'`; each is a `CameraRig` in `src/camera` producing a `CameraState`
(float64 position in ROOT, orientation, FOV, focus, exposure hints).

- **Cockpit**: eye at the commander's seat (`VehicleDef.cameras.cockpit`), free look with the mouse; the
  interior is ordinary scene geometry; `insideVesselId` switches audio to the cabin mix and exposure to
  interior metering.
- **Chase**: orbits the active vessel; orientation reference follows the navball mode (surface up near the
  ground, orbit plane in space) and blends between them; never clips into terrain (uses `TerrainProvider`).
- **Map**: detaches and orbits a focus body or vessel from 100 km to 2e9 m with exponential zoom; enables a
  small fill light and an exposure floor.
- Switching rigs blends position/orientation/FOV over about 0.6 s (`CameraRig.activate(from)`), so the view
  changes without a cut, a loading screen or a second scene.
- LOD observers = the camera plus every vessel near a surface, so terrain under the landing gear is at
  full detail even from a distant camera.

## 13. HUD and map view

- **HUD** (`src/ui`, `Hud`): altitude/speed readouts with surface/orbit toggle, navball with SAS mode
  buttons and all markers, throttle and g meters, stage stack with per-stage delta-v, resource bars, warp
  indicator, MET/UT, heat and chute envelope indicators, node burn info, notifications. It renders only
  from `SimSnapshot` (`Readouts`, `NavballState`, `staging`).
- **Navball** (`NavballRenderer`): a textured 3-D sphere rotated by `qVesselToHorizon` with projected
  markers, rendered by WebGPU to a 512 x 512 texture published as `'ui.navball'` for the HUD and the
  cockpit instrument.
- **MFD pages** (`MfdPainter`): Canvas 2D painters used by the cockpit displays; they share formatters with
  the HUD so numbers never disagree.
- **Map view** (`src/map`, `MapView`): samples each `Patch` conic in float64 to sub-pixel chord error,
  draws current and planned trajectories across SOI changes (relative to the patch body's current position,
  or at-intercept using `Patch.bodyPosAtEnd`), Ap/Pe/AN/DN/SOI/impact/closest-approach markers, body orbits
  and SOI shells, and maneuver nodes with six drag handles plus time dragging. All edits go through
  `PlayerCommands.addNode/setNode/removeNode`; the predicted patches come back in the next snapshot.

## 14. Audio

`src/audio` implements `AudioEngine`; it consumes `AudioFrame { snapshot, listener, realDt, warpFactor }`.

- Graph built by a factory that accepts any `BaseAudioContext`, so the same graph renders offline in tests
  (`OfflineAudioContext`) and live in the app. Buses: `engines`, `aero`, `reentry`, `events`, `cabin`, `ui`
  into `master`; an analyser on every bus feeds `AudioProbe`.
- Sources: per-engine layered loops driven by `throttleActual`, thrust and ambient pressure (crackle and
  far-field rumble fade with pressure); aerodynamic wind and transonic buffet from `q` and Mach; reentry
  roar from `plasmaIntensity`; one-shots from events (ignition, shutdown, staging/pyro, fairing, legs,
  chute deploy/inflate, touchdown, splash, RCS pulses, explosions); cabin ambience and structure creaks
  under g-load; UI clicks.
- **Two propagation paths**: airborne (gain and low-pass cutoff scale with ambient pressure at the listener
  and with distance; silent in vacuum) and structure-borne (through the hull; always present inside the
  cabin, heavily low-passed, and faintly for an external camera attached to the vessel). This is what makes
  vacuum "muffled" rather than mute.
- Listener = camera: cockpit vs external, position relative to nozzles (panning, distance attenuation and
  delay), all from `AudioListener`.
- Assets are generated at build time (`tools/audio`, keys from `.env`, never shipped) plus procedural
  synthesis, stored under `public/assets/audio/`, and listed in `data/defs/audio/`.
- Continuous sounds fade out above physics warp; events are suppressed during rails warp.
- The context is created suspended and resumed on the first real user gesture.

## 15. Testing

**Headless (vitest, Node).** Unit tests next to the code (`*.test.ts`), cross-module tests in
`tests/unit/<package>/`. The full mission is `tests/mission/` (`npm run test:mission`). The Python bake
library is checked against TypeScript golden files (`npm run golden`, `npm run test:py`).

**Browser (Playwright, real Chrome, real GPU).** `tests/browser/harness.ts` provides `openPage`,
`assertDiscreteGpu`, `expectNoErrors`, `saveScreenshot` (+ image statistics), `waitIdle`, `pngDiff`,
`withGpuLock`. Projects: `functional` (default, safe to run concurrently), `perf` (`*.perf.spec.ts`,
serialised by the machine-wide GPU lock), `mission` (the long acceptance flight).

**Labs.** Each package has `labs/<package>/` pages that run it alone against the FakeSim or scenario
states, and specs in `tests/browser/<package>/` that screenshot and measure them. `labs/template` and
`tests/browser/shell/lab-template.spec.ts` are the reference pattern.

**`window.__test`** (`TestApi`, base implementation `src/core/testing/testApi.ts`): `ready`, `errors`
(window errors, unhandled rejections, GPU uncaptured errors, shader compile errors, device loss),
`adapter`, `state()`, `milestones()`, `isIdle()`, `waitFrames(n)`, `perf()`, `setControls()`, `commands`,
`pilot`, view/camera helpers, `setDeterministic()`, `setPaused()`, `hdrStats()`, `audio()`, `map()`,
`page`. It is read-only with respect to physics.

Rules for browser tests: assert the adapter first; close loops on state with `waitForFunction` instead of
sleeping; read screenshots back and assert they are real images; never assert exact wheel deltas; perf
numbers only inside `withGpuLock`, with vsync on, from GPU timestamp queries; always discard warm-up frames.

**FakeSim** (`src/core/fakes/fakeSim.ts`) provides consistent snapshots for eight canned scenes (pad,
ascent, lowOrbit, translunar, lunarOrbit, lunarSurface, reentry, chutes). It is kinematic, not physics,
and is never used in the app or in mission tests.

## 16. Room for EVA (not built now)

Nothing below is a stub in shipped code; these are the seams that make EVA additive:

1. **Vessel-agnostic world.** The sim simulates a list of vessels; an astronaut is a vessel with one
   `evaSuit` part (RCS jetpack = an `rcs` module, `command` module with one seat). Free-floating EVA needs
   no new physics: rails/integration, SOI, warp, attitude hold and RCS translation already exist, and the
   physics bubble keeps several vessels at full fidelity.
2. **Controller seam.** Input reaches the sim through `ActiveController`. An `EvaController` maps the same
   `InputFrame` to jetpack translation, or drives a surface walker (capsule collider against
   `TerrainProvider.heightAt/normalAt`, gravity `mu/r^2`, `terrain.surfaceFriction`).
3. **Crew and hatches are data.** `VehicleDef.crew` binds crew to seats; the `command` module carries an
   optional `hatch`. "Go EVA" = move a crew member from a seat to a spawned suit vessel at the hatch.
4. **Camera seam.** Views are `CameraRig`s keyed by mode strings; first/third-person EVA rigs are new rigs.
5. **Terrain guarantee.** Collision surface = rendered surface near any LOD observer; an astronaut is one
   more observer. Rocks are both drawn and collidable from the same hash.
6. **Renderer.** Nothing assumes the camera is on a vessel; a character is one more drawable feature.

## 17. Performance budgets (RTX 5090, 60 fps)

| Budget | Target |
|---|---|
| GPU, sum of pass timestamps at 1440p internal (4K via TAAU) | p99 <= 11 ms |
| rAF delta with vsync | p99 <= 17.5 ms, no delta >= 33 ms in steady flight |
| CPU main thread per frame | p99 <= 6 ms (sim <= 1.5 ms at 4x physics warp, quadtree + cascades <= 1 ms, uploads <= 2 ms, UI <= 0.5 ms) |
| Tile generation | 6-12 ms per tile in workers; <= 8 uploads or 2 ms per frame |
| VRAM | about 3 GB (terrain 1.1, vehicle + materials 0.6, G-buffer/history 0.5, clouds/LUTs 0.2, shadows 0.13, sky 0.1) |
| Headless full mission | < 5 min wall-clock (target 90 s) |
| Baked data on disk | < 20 GB including caches |

Per-pass GPU estimates are in `rendering-design.md` section 13; each render package owns its line of that
table and proves it with a `*.perf.spec.ts` under the GPU lock. Dynamic resolution holds 60 fps if a
checkpoint exceeds budget, but the budget is measured at the stated internal resolution.

## 18. Definition of done and mission test plan

Done means a player can, in one browser session with no loading screens: launch from the pad, reach
orbit, fly to the Moon, land on real lunar terrain, lift off, return, survive reentry and splash down
under parachutes - flying every burn by hand - at 60 fps, with every body photoreal at every distance,
full sound, and no placeholder, stub or TODO anywhere.

### 18.1 Headless mission (vitest, `tests/mission`)

The scripted pilot flies `scenarios/lunar-direct` through the real `Sim` and the real `TerrainProvider`
(fs tile source, real baked tiles), calling only `step()` / `advanceRails()` / `peek()` / `setControls()` /
`commands`. The run fails on crew loss, loss of the command part, any NaN, a phase timeout,
`cheatCounter > 0`, or `scenario.startKind != 'pad'`. Milestones, in order, with gates
(`sim-design.md` 16.3):

1. `LIFTOFF` - surface speed at clamp release < 0.1 m/s; inertial speed 439 +/- 2 m/s (Earth rotation).
2. `MAX_Q` 20-40 kPa, no structural failure.
3. `STAGE_SEP_1`, `FAIRING_JETTISON` (above 80 km), `STAGE_SEP_2`, each leaving debris vessels.
4. `EARTH_ORBIT` - Pe >= 160 km, Ap <= 400 km; one rails revolution matches Kepler to 1 m.
5. `TLI_COMPLETE` - predicted patches contain a Moon encounter.
6. `MOON_SOI_ENTER` at the predicted time +/- 2 s.
7. `LUNAR_ORBIT` - e < 0.05, Pe > 60 km.
8. `LUNAR_TOUCHDOWN` - on full-resolution real terrain; vertical < 2.5 m/s, horizontal < 1.0 m/s, tilt
   < 12 deg, all legs intact; still landed after 600 s.
9. `LUNAR_LIFTOFF` - descent stage stays behind as landed debris.
10. `MOON_SOI_EXIT`, `EARTH_PERIGEE_TARGETED` (vacuum perigee 30-60 km).
11. `ENTRY_INTERFACE` at 122 km, 10.9-11.1 km/s; peak g < 10; g-dose < 5; ablator remaining > 25 %.
12. `DROGUE_DEPLOY`, `MAIN_DEPLOY` inside their envelopes, no chute failure.
13. `SPLASHDOWN` - on water, vertical speed <= 9.5 m/s, crew alive, floating upright after 30 s.
14. Budgets - mission under 14 days of sim time, no negative propellant, delta-v margins logged.

Re-running gives the same state hash (determinism). Supporting suites: Kepler/SOI/ephemeris/atmosphere
unit tests, per-stage delta-v, ascent-only, reentry corridor sweep, parachute envelope, leg drop tests,
buoyancy, SAS convergence, warp never steps past an event.

### 18.2 Browser mission (Playwright `mission` project)

`/?scenario=lunar-direct&pilot=1` in real Chrome on the RTX 5090: the same pilot, driven through
`Sim.advance(realDt, onControlTick)`, in real time with the allowed warp levels (about 20-25 minutes).
Short segments are additionally flown with real key presses to prove the bindings (throttle up, Space to
stage, SAS mode keys, M for the map, a node drag with the mouse). Judged on: the same milestone list and
gates read from `window.__test.milestones()`; `cheatCounter == 0`; `window.__test.errors` empty for the
whole flight; per-phase perf (rAF p95 < 16.7 ms, GPU p99 <= 11 ms at checkpoints taken under the GPU
lock); audio bus levels reacting at ignition, in vacuum and during reentry; screenshots at every
milestone in all three views saved for visual QA.

### 18.3 Visual and performance checkpoints

Deterministic screenshots (frozen presentation time, streaming idle) at: pad at noon and at sunset, 10 km,
40 km, LEO day / terminator / night side with city lights and stars, translunar Earth and Moon, low lunar
orbit at low sun, lunar touchdown, lunar surface from the cockpit, reentry peak heating, parachute
descent, splashdown. Each has an image-statistics assertion, a perf budget, and is reviewed by eye by the
lead. A LOD pop detector flies a scripted camera path with sim time frozen and asserts bounded
frame-to-frame image difference.

## 20. Main risks

| Risk | Mitigation |
|---|---|
| Ground-level realism at the pad from 10 m imagery | arid volcanic site, landcover-driven detail materials anchored to imagery colour, rocks, detailed pad complex, graded apron |
| Tile generation throughput | band-limited height function, worker pool, forced morph-in; fallbacks in `rendering-design.md` 15.2 |
| Clouds stable from ground to orbit | one march path; quality (not path) changes with altitude |
| Hand-flown lunar return corridor | lifting capsule + roll rule survives vacuum perigees of 10-65 km |
| Landing-site data resolution | NAC DTM region + calibrated procedural craters/regolith; collision = render by construction |
| Parallel teams diverging | contracts in `src/core`, golden files across languages, FakeSim, labs, scoped verification |
| Perf interference between concurrent test runs | machine-wide GPU lock for perf projects |
